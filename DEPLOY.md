# Deploying to Fly.io

The bot uses Telegram **long-polling**, so it runs as a single always-on worker (no public
HTTP). Wallet data is persisted on a Fly **volume** mounted at `/data`, so it survives
deploys and restarts.

## One-time setup

1. Install flyctl: https://fly.io/docs/flyctl/install/ — then `fly auth login`.
2. Pick a **globally-unique** app name and set it in `fly.toml` (`app = "..."`).
3. Create the app:
   ```bash
   fly apps create <app-name>
   ```
4. Create the volume in the **same region** as `primary_region`:
   ```bash
   fly volumes create galileo_data --size 1 --region iad --app <app-name>
   ```
5. Set secrets (these stay out of the image and the repo). **Use freshly-rotated values** —
   the ones currently in git history are compromised:
   ```bash
   fly secrets set \
     TELEGRAM_BOT_TOKEN=xxxxx \
     OPERATOR_PRIVATE_KEY=0x... \
     WALLET_ENCRYPTION_KEY=xxxxx \
     OG_COMPUTE_API_KEY=xxxxx \
     PROOFS_HASH_SALT=$(openssl rand -hex 32) \
     --app <app-name>
   ```
   (Other config — RPC, chain id, compute base URL/model — uses the defaults in `src/config.ts`;
   override any of them with more `fly secrets set` / `[env]` entries if needed.)

## Deploy

```bash
fly deploy
```

## Keep it to ONE instance

Telegram allows only one long-polling client per bot token, so run **exactly one** machine:

```bash
fly scale count 1 --app <app-name>
```

Running two or more causes `getUpdates` 409 conflicts (the bot will flap).

## Operate

```bash
fly logs --app <app-name>      # tail logs; look for "[startup] ... bot @YourBot is running"
fly status --app <app-name>    # machine + volume state
fly secrets list --app <app-name>
```

## Uptime monitoring & cron

The app exposes a tiny health endpoint at **`https://<app-name>.fly.dev/health`** →
`{"status":"ok","uptime":N}` (served by `src/health.ts`, port 8080 via `[http_service]`).

- **UptimeRobot / Better Stack:** add an HTTP(s) monitor on `https://<app-name>.fly.dev/health`,
  interval 5 min, expecting `200`. You'll get alerted if the bot goes down.
- **cron-job.org (or any cron pinger):** add a job hitting the same URL on a schedule. This is
  optional — `auto_stop_machines = false` already keeps the machine running 24/7; the ping just
  feeds your uptime history and acts as a backup heartbeat.

The endpoint confirms the process is alive (not that Telegram polling is healthy), which is
enough for down/restart alerts.

## Proof Index Generation

The `public/proofs.json` audit feed (served at `/proofs`) is generated by `scripts/generateProofIndex.ts`. It runs in two places:

- **GitHub Actions** (`.github/workflows/proofs.yml`) runs every 6 hours. The workflow uses dummy env vars to satisfy `config.ts` validation (the script never signs anything — it only reads from 0G Storage), and skips the commit when the script returns an empty index. This makes CI a heartbeat that proves the pipeline works without ever overwriting real data with empty content.
- **Fly machine** (on demand) is where real proof regeneration with user data happens — the persistent volume holds `OG_STORAGE_INDEX_PATH`. Trigger it with:

  ```bash
  fly ssh console --app <app-name> --command "npm run generate-proofs"
  ```

- **Manual run anywhere**: `npm run generate-proofs`.

## Secrets handling

- `.env` (and `.env.local`) are **gitignored** but still contain live secrets in your working tree. Treat them as sensitive:
  - Never commit them (even though gitignore should prevent it).
  - Never copy them into cloud-sync folders, backups, or shared drives without encryption.
  - Never paste their contents into chat, issues, or support tickets.
  - If you suspect a leak, **rotate immediately** via `fly secrets set` and update your local `.env` from the new values.
- For Fly, the only secrets that ever need to leave your machine are the `fly secrets set` invocations in the setup section above. The real secrets never enter git history.
- The deployed contracts (`WOG_ADDRESS`, `DEX_ROUTER_ADDRESS`, `DEX_FACTORY_ADDRESS`, `USDC_ADDRESS`, `USDT_ADDRESS`) are public on-chain — they are **not** secret. The `OPERATOR_PRIVATE_KEY` that controls the operator wallet **is** secret and should be rotated immediately if exposed.
- `PROOFS_HASH_SALT` anonymizes userIds in the public `proofs.json` feed (served at `/proofs`). It is **not** a credential — losing it does not compromise any wallet or signing key — but rotating it will cause all existing `userHash` values to change on the next regeneration, effectively restarting the public audit trail. Keep it stable across deploys. Treat leaks as low-severity: it only obscures the link between a Telegram userId and a public storage rootHash.

## Notes

- `WALLET_ENCRYPTION_KEY` must stay **stable** — changing it makes existing stored wallets
  undecryptable. Set it once via `fly secrets` and leave it.
- The volume is tied to one machine/zone; that's expected for a single-instance bot.
- Fly restarts the machine if the process exits.
